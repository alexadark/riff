№ 01

One shared system, native where it runs.

RIFF is a stage runner for one bounded repository change at a time. Its business instructions are shared semantic role specifications. Its runtime adapters carry the provider, model, reasoning effort, tools, permissions, sandbox, and delegation rules.

The separation is deliberate. A role says what good planning, implementation, review, diagnosis, security assessment, red-team testing, or load testing means. An adapter says how that role executes in a particular runtime. This keeps shared instructions portable and makes runtime policy inspectable.

The operating idea

RIFF turns a clear request into a verified result without hiding the work. A plan declares ownership and checks. Sequential autonomous waves implement that plan. Mechanical controls establish facts. Fresh reviewers judge independent evidence. The result is inspectable on disk before anyone decides to commit, merge, deploy, or promote.

Structure should make autonomy safer, not make the workflow heavier. RIFF, operating principle

Bounded by design

Principle 01

Every native run receives an explicit phase id and task. RIFF does not infer a roadmap item or resume a partial stage implicitly.

Adapters stay thin

Principle 02

Provider-specific settings belong in adapters. Shared role specifications do not name models or embed runtime permissions.

Evidence wins

Principle 03

Runner observations replace untrusted worker claims. State records a result; it is not permission to continue work.

№ 02

Codex native. Claude Code native.

Codex and Claude Code are native model providers for the same stage runner. The active RIFF profile selects one adapter family for the whole phase; shared specifications, autonomous waves, artifacts, gates, and completion rules remain identical.

Native provider

Codex

$next or $riff:next

Codex project-local skills and namespaced plugin skills expose the stage runner. Codex adapters enforce the Sol, Terra, and Luna route portfolio, isolated reviews, and closed runtime permissions.

  1. Use $next in a project-local installation.
  2. Use $riff:next from the namespaced plugin.
  3. Use $resync or $riff:resync to reconcile RIFF-owned runtime links.
Native provider

Claude Code

./.riff/riff next

Claude adapters map the same controller and seven semantic roles without redefining their business behavior. Each dispatch is fresh and non-persistent, ignores project customizations, and receives a closed tool and permission set.

  1. Set runtime.provider: claude in the active profile.
  2. Run the same provider-neutral riff next command.
  3. Use /riff:resync to reconcile an installation.
Provider selection

Set runtime.provider to codex or claude in the first active profile. A project profile takes precedence over the framework profile. Missing selection defaults to Codex; invalid selection fails before dispatch. An explicit --provider option is a one-run override recorded in the routing receipt. RIFF never falls back silently or changes provider during a phase.

The common deterministic base

The terminal CLI is the common deterministic boundary. It owns installation, phase management, status, dashboard lifecycle, native stages, autonomous roadmap waves, and resync across both providers. In this release, planned smoke commands use the Codex CLI only as a mechanical sandbox helper even when Claude is selected; no Codex model is dispatched on the Claude route.

№ 04

Inside native next.

One invocation handles one bounded phase. The runner owns the order. It validates each transition and persists completed only after every required gate has passed.

Preflight

Validate Git root, RIFF link, framework path, HEAD, lock, and writable artifact boundaries.

Controller

Classify the request and select declared runtime classes. Architecture or critical work gets a fresh confirmation.

Planner

Create PLAN.md with task ownership, numbered waves, boundaries, and structured smoke commands.

Plan validation

Reject malformed ownership, unsafe paths, invalid smoke commands, identity mismatches, and untrusted prompt injection patterns.

Fresh plan review

A read-only reviewer independently returns PROCEED or REVISE from an evidence snapshot.

Autonomous waves

Workers execute plan waves in order. Each worker receives only its assignment and owned paths.

Mechanical gates

Run declared smokes, validate the summary, and scope-check actual product changes.

Fresh code review

A separate read-only reviewer returns PASS or FAIL against the plan, delta, summary, and evidence.

Persist completion

Repeat mechanics after review, record hashes and route receipt, then persist completed state.

Autonomous, sequential waves

The planner declares every task exactly once under numbered waves and assigns exclusive owned paths. RIFF dispatches a worker for each wave in plan order without a user pause. Tasks may be independent in a wave, but the current native slice executes workers sequentially so each checked result becomes the next wave's starting point.

wave 1:
  - task 1: establish design tokens and approved assets

wave 2:
  - task 2: update the shared public shell

wave 3:
  - task 3: rebuild homepage sections
Retry boundary

Normal waves have no retry. Workers do not run PLAN smoke commands in the canonical staged workspace. RIFF runs those smokes after normal waves in disposable clones, then permits one bounded full-plan repair only after the first final smoke failure.

Autonomous roadmap waves and loops

Roadmap waves sit above a single native stage. riff wave --autonomous runs the current ready dependency frontier. Add --loop to recompute readiness and continue across phases until the roadmap is dry or a real stop condition is reached. This is distinct from the worker waves inside one PLAN.md.

./.riff/riff wave --autonomous
./.riff/riff wave --autonomous --loop
./.riff/riff wave --resume
./.riff/riff wave --status

Use $wave or $riff:wave in Codex and /riff:wave --autonomous --loop in Claude Code. Ordinary and security-sensitive implementation continues autonomously. Security hooks run once after product phases. Explicit visual or functional verification, destructive boundaries, promotion, blocking failures, and operator caps remain stop conditions. Wave state and safe-resume evidence live under .planning/riff-wave/.

№ 05

The seven semantic roles.

The role is the common business contract. The adapter is the runtime implementation. This is why the same role behavior can be surfaced through Codex and Claude without turning every role file into provider-specific prose.

Planner

Bounded plan and ownership

Creates tasks, owned paths, waves, boundaries, and smoke commands from a read-only snapshot.

Worker

Implement, fix, or simplify

Executes an approved assignment in the staged workspace and returns structured summary content.

Reviewer

Independent judgment

Reviews plan, code, architecture, roadmap, incident, or milestone evidence from a fresh read-only snapshot.

Debugger

Evidence-backed diagnosis

Diagnoses a failure and produces a bounded correction assignment. It returns report content, not direct product changes.

Security reviewer

Reachable security defects

Performs a read-only security assessment and returns a report for the appropriate gate.

Red teamer

Approved non-production proofs

Tests bounded attack hypotheses against approved targets while remaining repository-read-only and report-only.

Load tester

Static or approved scale evidence

Assesses performance risks statically or against an approved non-production target without repository writes.

What is not a role

ComponentCurrent responsibility
ControllerA native stage-control adapter, not an eighth semantic role.

ImproveAn explicit skill, not an agent.

The routine controller runs first. If it classifies planning as architecture or review as critical, RIFF runs one fresh architecture-controller confirmation. That confirmation is canonical for planner, worker, plan-reviewer, and code-reviewer selection.

Fast service tier

Every Luna adapter sets the Fast service tier while preserving its declared reasoning effort. Fast lowers latency and consumes more plan usage. Non-Luna adapters do not set that service tier.

№ 07

Gates produce inspectable facts.

Reviews are fresh and isolated. A plan reviewer sees the validated plan. A code reviewer sees the plan, worker summary, product files, and delta. Neither inherits the worker conversation or a prior reviewer’s private context.

Completion is not promotion

Completion requires a valid plan, PROCEED plan review, completed worker output, passing mechanics and scope, PASS code review, repeated mechanics, and persisted completed state. It does not create a commit, open a pull request, merge a branch, publish, deploy, or promote a project.

Explicit confirmation

Promotion is a separate skill. Promotion always requires user confirmation before RIFF changes project files. Visual verification and product acceptance remain separate decisions outside the native stage.

№ 08

Operating reference.

Before a stage, make the change legible. After a stage, read the evidence. Keep installation and publication as conscious human decisions.

Before you run

  1. Use a normal Git checkout with a resolvable HEAD. riff init does not support Git linked worktrees.
  2. Run riff init for a new project or riff resync after RIFF adds or removes active skills or adapters.
  3. Save external references, approved assets, preservation constraints, and runnable checks in project files.
  4. Name a safe phase id and the exact bounded task. State permitted surfaces and exclusions.
  5. Use only checks that exist and are meaningful for the project.

After completion

  1. Read SUMMARY.md, SCOPE-CHECK.json, REVIEW.md, and the stage state file.
  2. Perform any product-specific visual or manual verification that the stage does not cover.
  3. Decide separately whether to commit, open a pull request, merge, publish, deploy, or promote.
  4. Confirm promotion only when you intend to run it.

Operational limits

Production model and smoke dispatches require Darwin because the runner depends on read-deny sandbox enforcement. The runner fails closed elsewhere. The maintained Markdown manual contains the detailed procedures: RIFF Manual. The repository architecture guide is How it works.
